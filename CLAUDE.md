# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

GuitarTab: a browser guitar-tab editor and player (Vue 3 + TypeScript + Vite, Web Audio, VexFlow for standard notation). Imports Guitar Pro 3–8, MIDI and its own `.gt` format; exports `.gt`, GP5, GPX and MusicXML.

## Where things are

- The git repository is this folder (`guitartab/`). Planning docs live one level up, outside the repo: `../IMPROVEMENTS_AUDIT.md` (the working plan: numbered "Big wins"; "continue with the next big improvement" means this list), `../RELEASE_PLAN.md`, `../DEPLOYMENT.md`. CI is `.github/workflows/ci.yml` (unit + coverage, typecheck, lint, build budgets, Playwright on Linux); the old `../.github/workflows/guitartab-ci.yml` outside the repo never ran.
- `HANDOVER.md` is the detailed log of what was built, how it was verified and what was left. Read its sections 1, 4–7 before larger work; add a section when you finish one.
- `ARCHITECTURE.md` describes the current architecture in more depth than the section below (layers, startup, rendering, editing, playback, formats, bundle, known weak spots). Update it when you change how a subsystem works.

## Working rules for this repo

- **The user commits.** Don't commit, stash, reset or discard changes unless asked.
- Never commit `Empire Of The Sun - We Are The People v2.gp5` (copyrighted local benchmark file) or `test-results/`. Ask before committing `public/audio/` (large samples, unclear licence).
- Report verification honestly (test counts, flakes, what was only checked by reading code); the user reads summaries, not diffs, and values screenshots for visual changes.

- `npm run lint` covers all of `src` (`.vue` and `.ts`), tests, e2e and scripts. 26 warnings (complexity/length/any; most in code ported from the legacy core: the GP5 writer, `durationEditing`, `barFilling.fillBeat`, `computeBarWidth`) are known; errors are not acceptable.
- A husky pre-commit hook runs lint-staged (`eslint --fix`, Prettier on staged `.ts/.mjs`). `.prettierignore` keeps `src/assets/` and `*.vue` out of Prettier for now.

## Architecture (big picture)

Vue components render and forward input; the logic is in `src/services`, state in plain `reactive` modules in `src/stores`, pure helpers in `src/utils`. The old legacy core in `src/assets/js` is gone (ported phase by phase, HANDOVER 3.28–3.34; `tests/layering.test.ts` keeps it from coming back). `ARCHITECTURE.md` has the longer version.

**Song data.** `src/stores/songState.ts` is the reactive source of truth; `Song` (`stores/song.ts`, a `Proxy` over it with accessors) reads/writes through it, so direct edits are reactive. Shape: `Song.measures[track][block][voice][beat]`. A "block" is a bar (bar metadata in `Song.measureMeta[block]`); the type `Beat` is one beat. Use the accessors `Song.getBeat/findBeat/getNote(ref)` rather than indexing by hand. Optional features are optional fields (`beat.text`, `beat.chord`, `effects.stroke`, …); old `.gt` files are upgraded on load by `services/songMigrations.ts` (add a step there when changing a field). Use `toRaw` for bulk reads.

**String order.** Data string index 0 is the **lowest** string (pitch = tuning[string] + fret; same in GP files, MIDI, audio, notation), drawn on the **bottom** tab line. Convert with `stringLine()` (`utils/tabStrings.ts`) whenever a string becomes a screen position. Exception: chord `frets[]` are stored highest string first.

**Rendering pipeline.** `GuitarTabView.vue` → `useGuitarTabLayout` → `editorCore.buildModernTabRows` → `services/editor/measureLayoutEngine.ts` (the only row-breaking/width pipeline, incl. `computeBarWidth`; it writes the plain `tabLayout` arrays in `stores/tabLayoutState.ts` (`blockToRow`, `blocksPerRow`, `measureOffset`, …) that playback and navigation read; `redrawTrack` in `layoutInvalidation.ts` lays a track out again). Vertical layout uses per-row annotation lanes (`utils/tabRowLanes.ts`; row-local y, `y = 0` = top string). Layout is cached per block (`stores/tabRenderLayout.ts`) so unchanged bars don't re-render. Pitfall: the layout is computed inside a computed that writes reactive state; reads during that write must use `toRaw`, otherwise "Maximum recursive updates". Only visible rows are mounted (`useVisibleTabRows.ts`); anything that needs the whole tab in the DOM (PDF/SVG export, print) must wrap it in `withAllRowsRendered()`. Classical notation (VexFlow, lazy) draws one staff per visible row from layout metrics, never from drawn output (`services/notation/`: `classicalNotation.ts` converts and draws, `vexflowNotes.ts` the pure conversion, `classicalNotationAdapter.ts` loads it lazily; `ClassicalRowSurface.vue`). The installed `@types/vexflow` describe VexFlow 1.2 while VexFlow 4 runs: check new VexFlow calls against `node_modules/vexflow/build/types`.

**Events and state.** `utils/typedEventBus.ts` is the only event bus (`render.*`, `navigation.*`, `song-data-changed`, a few `ui.*`). Settings are the reactive `stores/settingsState.ts` (persisted per key; imported as `Settings`); `EPSILON`/`OVERBAR_ROW_HEIGHT` are constants exported there. `classicalNotationLayoutState.active` is not a mirror of `Settings.vexFlowIsActive` but means "classical layout metrics are ready". The toolbar's pressed/disabled buttons are a `computed` (`composables/useToolbarState.ts`) over the cursor, range and song, so no event is needed to refresh them. Banner messages: `showNotification(text, kind, action?)` in `stores/notificationState.ts` (rendered by `App.vue`); `showUserError` wraps it. The edit cursor and the range selection live in the reactive `stores/selectionState.ts` (read and write `selectionState.cursor` directly). The range is driven by `services/editor/rangeSelection.ts` (`startRange`, `extendRange`, `applyRangeAsLoop`, `clearRange`, `currentLoopInterval`, `notesInRange`, `rangeHasNotes`), which also owns the loop interval. `useTabSelection().currentSelection` is a further mirror; `navigation.setClickedPos` moves the cursor.

**Layering.** `services/`, `stores/`, `utils/`, `types/` and `data/` must not import `components/` or `composables/` (ESLint `no-restricted-imports`, and `tests/layering.test.ts`). Module-level reactive state goes in `stores/`, not in `composables/` (that folder is for functions used in component setup).

**Editing and undo.** Every undoable edit is an `EditCommand` on the one undo history in `services/editor/editCommands.ts` (`undoHistory.undo/redo/peek/clear/adaptToTrackRemove`, reactive `undoAvailability`; there is no `revertHandler` any more). Most edits use `recordBarEdit(label, { trackId, blockIds, allTracks? }, mutate)`: it snapshots the bars before and after `mutate` and records one step (no hand-written inverse; restores in place so held beat/note references stay live; `mutate` returning false or throwing rolls back). It nests: low-level mutators (`setFret`/`deleteNote` in `noteCommands.ts`, `changeNoteDuration`) record themselves, and a caller that wraps several in `recordBarEdit`/`editTransaction` gets one undo step; commands executed inside join it too. Pass `withoutUndo = true` to those mutators only when building a song (demo, tests). Note lengths and tuplets: `services/editor/durationEditing.ts` (`isNotePlaceable`, `setTuplet`, `changeBeatDuration`, which returns `{ applied, rescale }`: only `applied: false` may reach `recordBarEdit` as `false`, since that rolls the edit back); bar filling and tuplet numbering: `barFilling.ts`; tuplet bookkeeping: `stores/tupletState.ts`; zoom: `services/editor/zoom.ts` (`Settings.currentZoom` is the only zoom value). Other commands: `setValue`, `executeCommand`, `songSettingsCommands.ts` (song tempo, track volume, chord library, `recordTrackEdit` for track settings), `measureStructureCommands.ts` (add/remove bar), `recordSongInfoEdit` (title, artist…). Dialogs that edit beats, notes or bar settings use the generic `EditModalHandler` in `services/dialogs/effectModals.ts`: a config with `defaults`/`read`/`scope`/`write`; the Vue dialog binds `handler.form` and calls `handler.apply()` (one undo step, re-render, close). Add new simple dialogs there; bend, tremolo bar, time signature, chords and track settings have their own handlers. Every command re-renders, refreshes the toolbar and emits `song-data-changed` (autosave). Edits without undo, by choice: mute/solo/pan/effect knobs, master volume, the studio panels. All keyboard shortcuts are one table, `utils/keyboardShortcuts.ts` (`SHORTCUTS`), dispatched by `handleKeyDown` in `services/editor/keyboardDispatch.ts` (document, capture phase; `shortcutHandlers` there); the Help sheet is generated from the same table, so add new shortcuts there. Note entry at the cursor (typing frets, `placeNote`, deleting the note or the loop range, moving the cursor) is `services/editor/noteEntry.ts`; loading a song and switching tracks are in `services/editor/trackLoading.ts` (`loadSongIntoEditor`, `switchTrack`, `initTrackPlayback`, `resetEditorState`), fitting bars to a time signature in `services/editor/timeSignatureCommands.ts`. There is no Pinia: state is plain `reactive` modules in `stores/` (the note length for new notes is `stores/noteInputState.ts`; the sequencer's edit mode, playback indicator, dragged bar range and the fader meter canvases are `stores/sequencerState.ts`). MIDI input devices are listed and connected by `services/midi/devices.ts` (access is requested when the MIDI dialog opens); `services/midi/liveInput.ts` sounds live notes, shows them on the piano/guitar and writes recorded notes (one undo step per flush), placing pitches on strings with `services/midi/noteArranger.ts`. Dialogs whose Vue component does everything use `definePlainModal(id, name)` (`services/dialogs/baseModalHandler.ts`, reactive `params`). Dialog handlers and the registry (`modalTypes.ts`, `modalManager`) are `services/dialogs/`, not next to the `.vue` files, because the registry builds every handler at startup and services use it; the compressor and equalizer handlers control the master limiter and EQ, which `audioGraph.createBusses()` hands them. Copy/paste of the range selection is `services/editor/clipboard.ts` (copies are snapshots); the toolbar's effect switches on the song are `services/editor/effectToggles.ts`.

**Playback.** `services/playback/`; the app calls the `playback` object (`index.ts`: `togglePlayback`, `start`/`stop`, `setPlayPosition`, `jumpToBeat`, `jumpToPosition(block, ticks, beat)`, `adaptToLoopChange`…). `songCursor.ts` (pure: `BarSequence` = bars in playing order through repeats, voltas and the loop; the next beat of a voice; tuplets count at their played length), `scheduler.ts` (a worker, `timerWorker.ts`, ticks `scheduler.tick()` every 25 ms; it advances the song clock and schedules beats `scheduleAhead` (0.4 s) ahead on the `AudioContext` clock; metronome, count-in, speed trainer, jumps; after a loop jump the bar clock continues at the loop start), `notePlayback.ts` (how a beat sounds: mute/solo, ties, strums, grace and ghost notes), `playhead.ts` (the animation loop: position, piano/guitar, scrolling, playhead glide), `startPosition.ts` (where Play starts, in ticks). The song clock counts whole notes; convert with `spw()/wps()` (`tempo.ts`), which apply the practice speed (`stores/practiceState.ts`). Audio is `services/audio/`: `audioGraph` (the one AudioContext, track and drum buses, master EQ/limiter), `samplePlayer` (`playFret`/`playPitch`: SoundFont notes with their effects), `drumKit`, `metronome`, `meters`. Instruments come from a 25 MB SoundFont parsed on the main thread (`soundFont/`: `parseSoundFont` → `buildBanks`, loaded by `loadSoundFont`); each track bus has a chorus and a small Freeverb (`effects.ts`, disposed when the buses are rebuilt). Unit tests stub only `audioGraph` (it creates the AudioContext on import); `tests/audioEngine.test.ts` logs the graph on a fake AudioContext. Note lengths in ticks (whole = 64) are `utils/duration.ts`. Beat grouping and bar-local beat x: `services/editor/beatGrouping.ts`; a bar's left offset: `barLeftOffset` in `utils/measureBeatLayout.ts`. The piano and guitar dialogs render `stores/soundingNotesState.ts`: the beat playback has reached plus live notes (MIDI keyboard, piano clicks).

**Import/export.** `importSongBytes` in `services/songImport.ts` is the single import path (typed `ImportError`, rolls back on failure; `openSongFile` for the file picker, `loadGtBytes`, `loadBuiltSong`). GP3/4/5: `services/import/guitarPro/` (`parseGuitarPro(format, bytes)` → `applyGuitarProSong`; parser classes over a `ByteReader`; GP4/GP3 reuse the GP5/GP4 parts explicitly). GP6/7/8: `services/gpContainers.ts` (ZIP/BCFZ/BCFS) → `services/gpifImport.ts`. MIDI: `services/import/midiFile.ts` (`parseMidiFile`, the Standard MIDI File reader) → `services/midiImport.ts` (`buildSongFromMidi`). Exports (lazy `songExport` chunk): `musicXmlExport.ts`, `gpifExport.ts` + `gpxWriter.ts`, `gp5Export.ts` (`writeGp5(source)`, `currentSongAsGp5()`), `.gt` (`utils/gtSerialization.ts`). Parsers build plain data first and then apply it (`parseGpif` → `applyGpifSong`, `parseGuitarPro` → `applyGuitarProSong`), which keeps them testable in node: `tests/guitarProImport.test.ts` pins GP3/GP4 (files built byte by byte in `tests/helpers/guitarProBytes.ts`, there are no real ones in the repo) and the GP5 showcase against JSON snapshots in `tests/__snapshots__/guitarPro/`, plus a GP5 write → read roundtrip.

**Layouts.** `stores/layoutModeState.ts`: under 900 px a compact phone layout (`components/compact/`: `CompactBar`, `TouchNotePad`; desktop chrome stays mounted but hidden because legacy code finds elements by id), 900–1199 px desktop chrome with the sheet fitted to the window, wider the fixed desktop sheet. Sheet fitting and pinch zoom: `services/compactLayout.ts`. `?layout=compact|desktop` forces a layout.

**Startup and bundle.** `App.vue` → `startUp()` in `services/startup.ts` (first visit loads the demo song from `data/demoArrangement.ts`; e2e uses the small riff in `data/demoSong.ts`). Chunks are assigned in `vite.config.ts` (`MODULE_CHUNKS`, `EDITOR_CORE_PATHS`, `manualChunks`; Rollup pulls a named chunk's unassigned dependencies into it, so shared startup code needs a named chunk) and each has a size budget in `scripts/check-bundle-budget.mjs` (entry 16 KB, `toolbar` = `Menu.vue` 32 KB, `editor-core` 280 KB). `editor-core` holds the editor, playback/audio, dialog handlers and importers together because they import each other: two chunks that import each other crash only the production build ("Cannot access 'x' before initialization"; the dev server is fine), and `check:bundle` fails on such cycles. New startup code should be lazy or go into a named chunk; check `npm run build:check` and `vite preview` after moving modules between chunks.

## Tests

- **Vitest runs in `node`.** Opt into a DOM per file: `// @vitest-environment happy-dom` (components), `// @vitest-environment jsdom` (XML: happy-dom rejects CDATA). Legacy singletons that need a browser are mocked only where a file opts in, with the one-line `vi.mock(..., () => import('./helpers/legacyMocks').then(...))` pattern (see `tests/helpers/legacyMocks.ts`). Mock `Song` with `tests/helpers/songMock.ts`. `tests/playbackScheduler.test.ts` shows how to drive the real scheduler on fake timers; `tests/playbackCharacterization.test.ts` logs everything playback does per scenario (file snapshots in `tests/__snapshots__/playback/`).
- **E2E tests drive the app through its own modules**: `await import('/src/stores/song.ts')` inside `page.evaluate` (works because Playwright runs against the Vite dev server). Song `notes` arrays are sparse; use `Array.from(notes, …)`, not `.map`.
- `waitForEditorShell(page)` (`e2e/helpers.ts`) loads the small one-track riff (frets 0, 2, 3, so assert other frets); `{ demo: 'arrangement' }` gives the four-track demo. It waits for `html[data-editor-ready]`; tests that play audio also call `waitForSoundFont(page)` (`data-soundfont-ready`). No `networkidle` waits.
- Phone tests are `e2e/*.mobile.spec.ts` (run only in the `mobile` project). Long songs: `growSong()` or the effects fixture (`e2e/fixtures/effectsShowcase.ts`) with the overlap detector, never the user's GP5 file.
- Screenshot baselines (`e2e/classical-notation.spec.ts-snapshots/`, `e2e/visual*.spec.ts-snapshots/`) are per OS: `win32` locally, `linux` from CI. Refresh after an intended visual change with `--update-snapshots`.
- For visual checks write throwaway specs as `e2e/zz-*.spec.ts`, pass the output folder via an env var, and delete them afterwards.

## Code style

- TypeScript: no semicolons (Prettier). `.vue` files aren't formatted by Prettier yet; match the file you're in. Short comments that explain *why*.
- Toolbar popovers must `Teleport` to `<body>` (`#completeBar` clips overflow).
- **Icons:** `<AppIcon name="…" />` (`components/AppIcon.vue`, names typed from the generated `src/assets/icons/icons.ts`). Add an icon by putting an SVG into `src/assets/icons/source/` and running `npm run icons`; draw it in one dark colour (it becomes `currentColor`). No `<img>` icons and no filters for dark mode; instrument illustrations in `public/instrumentIcons` are the exception.
- **Colours come from `src/assets/css/tokens.css` only** (`tests/designTokens.test.ts` fails on literals elsewhere, in styles, templates and TS). Use the semantic tokens (`--color-*`, `--tab-*`, `--editor-*`, `--seq-*`); their dark values are under `#darkMode` there, so components need no dark-mode rules. In SVG markup set colours as `style="fill: var(--…)"` (attributes can't take `var()`). A token defined from another themed token must be declared on `:root, #darkMode` (see the block at the end of tokens.css).
