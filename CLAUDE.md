# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

GuitarTab: a browser guitar-tab editor and player (Vue 3 + TypeScript + Vite, Web Audio, VexFlow for standard notation). Imports Guitar Pro 3–8, MusicXML, MIDI and its own `.gt` format; exports `.gt`, GP5, GPX, MusicXML and MIDI.

## Where things are

- The git repository is this folder (`guitartab/`). Planning docs live one level up, outside the repo: `../IMPROVEMENTS_AUDIT.md` (the working plan: numbered "Big wins"; "continue with the next big improvement" means this list), `../RELEASE_PLAN.md`, `../DEPLOYMENT.md`. CI is `.github/workflows/ci.yml` (unit + coverage, typecheck, lint, build budgets, Playwright on Linux); the old `../.github/workflows/guitartab-ci.yml` outside the repo never ran.
- `HANDOVER.md` is the detailed log of what was built, how it was verified and what was left. Read its sections 1, 4–7 before larger work; add a section when you finish one.
- `ARCHITECTURE.md` describes the current architecture in more depth than the section below (layers, startup, rendering, editing, playback, formats, bundle, known weak spots). Update it when you change how a subsystem works.

## Working rules for this repo

- **The user commits.** Don't commit, stash, reset or discard changes unless asked.
- Never commit `Empire Of The Sun - We Are The People v2.gp5` (copyrighted local benchmark file) or `test-results/`. Ask before committing `public/audio/` (large samples, unclear licence).
- Report verification honestly (test counts, flakes, what was only checked by reading code); the user reads summaries, not diffs, and values screenshots for visual changes.

## Architecture (big picture)

Vue components render and forward input; the logic is in `src/services`, state in plain `reactive` modules in `src/stores`, pure helpers in `src/utils`. The old legacy core in `src/assets/js` is gone (ported phase by phase, HANDOVER 3.28–3.34; `tests/layering.test.ts` keeps it from coming back). `ARCHITECTURE.md` has the longer version.

**Song data.** `src/stores/songState.ts` is the reactive source of truth; `Song` (`stores/song.ts`, a `Proxy` over it with accessors) reads/writes through it, so direct edits are reactive. Shape: `Song.measures[track][block][voice][beat]`. A "block" is a bar (bar metadata in `Song.measureMeta[block]`); the type `Beat` is one beat. Use the accessors `Song.getBeat/findBeat/getNote(ref)` rather than indexing by hand. Optional features are optional fields (`beat.text`, `beat.chord`, `beat.lyrics`, `effects.stroke`, …); old `.gt` files are upgraded on load by `services/songMigrations.ts` (add a step there when changing a field). Use `toRaw` for bulk reads.

**String order.** Data string index 0 is the **lowest** string (pitch = tuning[string] + fret; same in GP files, MIDI, audio, notation), drawn on the **bottom** tab line. Convert with `stringLine()` (`utils/tabStrings.ts`) whenever a string becomes a screen position. Exception: chord `frets[]` are stored highest string first.

**Rendering pipeline.** `GuitarTabView.vue` → `useGuitarTabLayout` → `editorCore.buildModernTabRows` → `services/editor/measureLayoutEngine.ts` (the only row-breaking/width pipeline, incl. `computeBarWidth`; it writes the plain `tabLayout` arrays in `stores/tabLayoutState.ts` (`blockToRow`, `blocksPerRow`, `measureOffset`, …) that playback and navigation read; `redrawTrack` in `layoutInvalidation.ts` lays a track out again). Vertical layout uses per-row annotation lanes (`utils/tabRowLanes.ts`; row-local y, `y = 0` = top string). Layout is cached per block (`stores/tabRenderLayout.ts`) so unchanged bars don't re-render. Pitfall: the layout is computed inside a computed that writes reactive state; reads during that write must use `toRaw`, otherwise "Maximum recursive updates". Only visible rows are mounted (`useVisibleTabRows.ts`); anything that needs the whole tab in the DOM (PDF/SVG export, print) must wrap it in `withAllRowsRendered()`. Classical notation (VexFlow, lazy) draws one staff per visible row from layout metrics, never from drawn output (`services/notation/`: `classicalNotation.ts` converts and draws, `vexflowNotes.ts` the pure conversion, `classicalNotationAdapter.ts` loads it lazily; `ClassicalRowSurface.vue`). The installed `@types/vexflow` describe VexFlow 1.2 while VexFlow 4 runs: check new VexFlow calls against `node_modules/vexflow/build/types`.

**Events and state.** `utils/typedEventBus.ts` is the only event bus (`navigation.*`, `song-data-changed`, a few `ui.*`). Re-rendering is not an event: commands bump version counters in `stores/renderVersionState.ts` (`song`, per bar `bars['track:bar']`, `chords`) through `services/editor/renderCommands.ts` (`requestBlocksRender`, `requestFullRender`, …), `recordBarEdit` bumps the changed bars on every edit/undo/redo, and the tab layout computed reads `renderVersionState.song`. Settings are the reactive `stores/settingsState.ts` (persisted per key; imported as `Settings`); `EPSILON`/`OVERBAR_ROW_HEIGHT` are constants exported there. `classicalNotationLayoutState.active` is not a mirror of `Settings.vexFlowIsActive` but means "classical layout metrics are ready". The toolbar's pressed/disabled buttons are a `computed` (`composables/useToolbarState.ts`) over the cursor, range and song, so no event is needed to refresh them. Every toolbar action is an entry in `services/editor/toolbarActions.ts` (`TOOLBAR_ACTIONS`: element id, label, icon, group, shortcut, `run()`); `Menu.vue` (top bar `#tabBar` + edit bar `#statusBars` with tabs) and the note menu (`components/toolbar/NoteMenu.vue`: right-click, Shift+F10, long-press; popover on desktop, sheet on phones) render from it, so add a new tool there. Narrow bars fold groups into menus (`utils/toolbarFit.ts` + `composables/useToolbarFit.ts`). Banner messages: `showNotification(text, kind, action?)` in `stores/notificationState.ts` (rendered by `App.vue`); `showUserError` wraps it. The edit cursor and the range selection live in the reactive `stores/selectionState.ts` (read and write `selectionState.cursor` directly). The range is driven by `services/editor/rangeSelection.ts` (`startRange`, `extendRange`, `applyRangeAsLoop`, `clearRange`, `currentLoopInterval`, `notesInRange`, `rangeHasNotes`), which also owns the loop interval. `useTabSelection().currentSelection` is a further mirror; `navigation.setClickedPos` moves the cursor.

**Layering.** `services/`, `stores/`, `utils/`, `types/` and `data/` must not import `components/` or `composables/` (ESLint `no-restricted-imports`, and `tests/layering.test.ts`). Module-level reactive state goes in `stores/`, not in `composables/` (that folder is for functions used in component setup).

**Editing and undo.** Every undoable edit is an `EditCommand` on the one undo history in `services/editor/editCommands.ts` (`undoHistory.undo/redo/peek/clear/adaptToTrackRemove`, reactive `undoAvailability`; there is no `revertHandler` any more). Most edits use `recordBarEdit(label, { trackId, blockIds, allTracks? }, mutate)`: it snapshots the bars before and after `mutate` and records one step (no hand-written inverse; restores in place so held beat/note references stay live; `mutate` returning false or throwing rolls back). It nests: low-level mutators (`setFret`/`deleteNote` in `noteCommands.ts`, `changeNoteDuration`) record themselves, and a caller that wraps several in `recordBarEdit`/`editTransaction` gets one undo step; commands executed inside join it too. Pass `withoutUndo = true` to those mutators only when building a song (demo, tests). Note lengths and tuplets: `services/editor/durationEditing.ts` (`isNotePlaceable`, `setTuplet`, `changeBeatDuration`, which returns `{ applied, rescale }`: only `applied: false` may reach `recordBarEdit` as `false`, since that rolls the edit back); bar filling and tuplet numbering: `barFilling.ts`; tuplet bookkeeping: `stores/tupletState.ts`; zoom: `services/editor/zoom.ts` (`Settings.currentZoom` is the only zoom value). Other commands: `setValue`, `executeCommand`, `songSettingsCommands.ts` (song tempo, track volume, chord library, `recordTrackEdit` for track settings), `measureStructureCommands.ts` (add/remove bar), `recordSongInfoEdit` (title, artist…). Dialogs that edit beats, notes or bar settings use the generic `EditModalHandler` in `services/dialogs/effectModals.ts`: a config with `defaults`/`read`/`scope`/`write`; the Vue dialog binds `handler.form` and calls `handler.apply()` (one undo step, re-render, close). Add new simple dialogs there; bend, tremolo bar, time signature, chords and track settings have their own handlers. Every command re-renders, refreshes the toolbar and emits `song-data-changed` (autosave). Edits without undo, by choice: mute/solo/pan/effect knobs, master volume, the studio panels. All keyboard shortcuts are one table, `utils/keyboardShortcuts.ts` (`SHORTCUTS`), dispatched by `handleKeyDown` in `services/editor/keyboardDispatch.ts` (document, capture phase; `shortcutHandlers` there); the Help sheet is generated from the same table, so add new shortcuts there. Note entry at the cursor (typing frets, `placeNote`, deleting the note or the loop range, moving the cursor) is `services/editor/noteEntry.ts`; loading a song and switching tracks are in `services/editor/trackLoading.ts` (`loadSongIntoEditor`, `switchTrack`, `initTrackPlayback`, `resetEditorState`), fitting bars to a time signature in `services/editor/timeSignatureCommands.ts`. There is no Pinia: state is plain `reactive` modules in `stores/` (the note length for new notes is `stores/noteInputState.ts`; the sequencer's edit mode, playback indicator, dragged bar range and the fader meter canvases are `stores/sequencerState.ts`). MIDI input devices are listed and connected by `services/midi/devices.ts` (access is requested when the MIDI dialog opens); `services/midi/liveInput.ts` sounds live notes, shows them on the piano/guitar and writes recorded notes (one undo step per flush), placing pitches on strings with `services/midi/noteArranger.ts`. Dialogs are state (Big win 30): `stores/dialogState.ts` holds the open windows and their stacking order; open one with `openDialog(DIALOGS.X, params)` / `toggleDialog` / `closeDialog` from `services/dialogs/dialogs.ts` (ids and footer names; it lazy-loads the handler registry `dialogHandlers.ts` and calls the handler's `openModal`). Handlers fill reactive state and never touch the DOM; the component binds it and calls the handler's methods, getting its handler with `getDialogHandler(id)`. `BaseModal.vue` renders the window from the store and drags/resizes it with pointer events (`resize="x"|"xy"`; interact.js is gone); `ModalsContainer` mounts each dialog component (an async chunk) on its first opening and handles Escape. Nothing is mounted before a dialog opens, so tests and code never look for a dialog's DOM before opening it. Dialogs whose Vue component does everything use `definePlainModal(DIALOGS.X)` (`services/dialogs/baseModalHandler.ts`, reactive `params`). The master EQ and limiter settings are audio services (`services/audio/masterEqualizer.ts`, `masterCompressor.ts`) that `audioGraph.createBusses()` wires; their panels only edit them. Each track has an optional channel EQ and compressor (`track.eq`, `track.compressor`, `services/audio/trackInserts.ts`; `TrackBus.setEq/setCompressor` put them in the bus only while they change the sound); the same panels edit them when opened with `{ trackId }` (`components/audio/channelTargets.ts`), from the Mixer's track strips (`Mixer.vue`: views "Tracks" `audio/TrackMixer.vue` and "Drum kit" `audio/DrumKitMixer.vue`; mixer edits have no undo). Lyrics (`beat.lyrics[verse]`, a trailing `-` hyphenates): pure core `utils/lyrics.ts` (Guitar Pro lyric text, flowing syllables over note beats), entry at the cursor `services/editor/lyricsEntry.ts` + `components/tab/LyricsEntryField.vue` (Shift+L; L is the tie), lane `lyrics` in `tabRowLanes.ts`; read from GP4/5/GPIF, written to GP5/GPX/MusicXML. Editing ergonomics (audit Big win 8): Shift+arrows/Shift+click/Ctrl+A select (`selectionCommands.ts`, also `transposeSelection` with `utils/transpose.ts`), rhythm keys `.`/Alt+3…/R/L/Insert/Ctrl+Delete (`rhythmCommands.ts`); both are the lazy `editing-tools` chunk, so editor code reaches them with `import()` (a static import from editor-core would pull them back or make a chunk cycle). `insertBars` (`measureStructureCommands.ts`) inserts bars in the middle; `padBarWithRests` (`barFilling.ts`) fills short bars, also on load. Voice 2 is drawn in `--tab-voice2`, the other voice faintly behind (`utils/otherVoiceNotes.ts`); a click on a faint note edits that voice. Score view (Big win 25, `Settings.scoreView`): `services/editor/scoreLayout.ts` lays the shown tracks (`stores/scoreViewState.ts`) out per system with shared rows and bar widths, through the per-track pass in `measureLayoutEngine.ts` (`beginTrackLayout`/`breakIntoRows`/`layoutRow`); rows then carry `trackId`/`voiceId`, and the edited track is still `Song.currentTrackId` (a click in another staff or Alt+↑/↓ switches, `scoreViewCommands.ts`). It excludes classical notation. Accessibility (Big win 10): dialogs get focus/Escape/Tab from `services/a11y/dialogFocus.ts` (used by `BaseModal`/`ModalsContainer`, lazy `dialog-shell` chunk); speak to screen readers with `announce()` (`stores/announcerState.ts`); toolbars opt into arrow-key movement with `data-roving-toolbar`; `--color-text-faint` is for disabled/placeholder only, readable text uses `--color-text-muted` or stronger (`tests/tokenContrast.test.ts` checks the token pairs, `e2e/accessibility.spec.ts` runs axe on every dialog). Copy/cut/paste of the range selection (or the cursor's beat) is `services/editor/clipboard.ts` (copies are snapshots; `pasteAsNewBars`); the toolbar's effect switches on the song are `services/editor/effectToggles.ts`.

**Playback.** `services/playback/`; the app calls the `playback` object (`index.ts`: `togglePlayback`, `start`/`stop`, `setPlayPosition`, `jumpToBeat`, `jumpToPosition(block, ticks, beat)`, `adaptToLoopChange`…). `playOrder.ts` (pure: `nextPlayedBar` = the bar after a bar through repeats, voltas and navigation signs D.C./D.S./Coda/Fine (`measureMeta.directionTargets/directionJumps`, `utils/directions.ts`); `buildPlayOrder` unrolls a song), `songCursor.ts` (pure: `BarSequence` = those steps plus the loop, a few bars ahead; the next beat of a voice; tuplets count at their played length), `scheduler.ts` (a worker, `timerWorker.ts`, ticks `scheduler.tick()` every 25 ms; it advances the song clock and schedules beats `scheduleAhead` (0.4 s) ahead on the `AudioContext` clock; metronome, count-in, speed trainer, jumps; after a loop jump the bar clock continues at the loop start), `notePlayback.ts` (how a beat sounds: mute/solo, ties, strums, grace and ghost notes), `playhead.ts` (the animation loop: position, piano/guitar, scrolling, playhead glide), `startPosition.ts` (where Play starts, in ticks). The song clock counts whole notes; convert with `spw()/wps()` (`tempo.ts`), which apply the practice speed (`stores/practiceState.ts`). Audio is `services/audio/`: `audioGraph` (the one AudioContext, track and drum buses, master EQ/limiter), `samplePlayer` (`playFret`/`playPitch`: SoundFont notes with their effects), `drumKit`, `metronome`, `meters`. Instruments come from the GeneralUser GS SoundFont, streamed (Big win 32): an 8 MB SF3 with a hashed name named by the tracked `public/audio/manifest.json` (made with `scripts/convert-soundfont.mjs`; file not in git, uploaded by hand), the song's presets first by HTTP range requests (`soundFont/streaming.ts`, lazy chunk `soundfont`; `soundFontState.loadedPresets`), the SF2 whole as fallback and with `SOUNDFONT_MANIFEST=off`; parsed on the main thread (`soundFont/`: `parseSoundFont` → `buildBanks` (global zones, layers, velocity, stereo voices), `envelope.ts` (SF2 envelopes, filter, LFOs), `sf3.ts` (Ogg Vorbis samples: `decodeAudioData`, WASM decoder as lazy fallback; `?soundfont=musescore` loads MuseScore_General.sf3), loaded by `loadSoundFont`, progress in `stores/soundFontState.ts`; Play pressed while it loads waits for it, so e2e tests that play must `waitForSoundFont`); each track bus has a chorus and a small Freeverb (`effects.ts`, disposed when the buses are rebuilt), and an optional amp and cabinet simulation in front of its pan (`TrackBus.setAmp`; settings `track.amp`, default on for GM 29/30 which then play the clean guitar samples, `ampModel.ts`; the DSP is the lazy `amp-sim` chunk `ampSimulator.ts`; edited in the sequencer's Amp column, `TrackAmpPanel.vue`; GP5 RSE tone names and GP6–8 sound/effect names switch it on at import). Unit tests stub only `audioGraph` (it creates the AudioContext on import); `tests/audioEngine.test.ts` logs the graph on a fake AudioContext. Note lengths in ticks (whole = 64) are `utils/duration.ts`. Beat grouping and bar-local beat x: `services/editor/beatGrouping.ts`; a bar's left offset: `barLeftOffset` in `utils/measureBeatLayout.ts`. The piano and guitar dialogs render `stores/soundingNotesState.ts`: the beat playback has reached plus live notes (MIDI keyboard, piano clicks). Audio export (Big win 29, File → Export audio, lazy chunk `audio-export` = `services/audioExport/`): `renderPlan.ts` (pure timeline) → `audioRender.ts` (an `OfflineAudioContext` graph copied from the live one with `createBusses(audioGraph)`/`copyBussesOf`, its own `SamplePlayer(graph)`, beats through `notePlayback.playBeat(…, target)`) → WAV (`wavFile.ts`) or Ogg Opus (`opusEncoder.ts` WebCodecs + `oggOpus.ts`); state in `stores/audioExportState.ts`. A practice-speed change while playing re-schedules the queued 0.4 s (`samplePlayer.cancelFrom`).

**Import/export.** `importSongBytes` in `services/songImport.ts` is the single import path (typed `ImportError`, rolls back on failure; `importSongFile` loads lazy readers first (Guitar Pro 3–8 since Big win 30, MIDI, MusicXML; so open anything but `.gt` with `importSongFile`, also in e2e), `openSongFile` for the file picker, `loadGtBytes`, `loadBuiltSong`). GP3–8 readers are the lazy chunk `gp-import` (facade `services/import/guitarProReaders.ts`); `applyGpifSong` and the `GpifSong` shape are `services/import/songData.ts` (startup: the demo uses them). GP3/4/5: `services/import/guitarPro/` (`parseGuitarPro(format, bytes)` → `applyGuitarProSong`; one version-parameterized reader, `parser.ts` + `beatReader.ts`, over a `ByteReader`; each `version` check is one format difference). GP6/7/8: `services/gpContainers.ts` (ZIP/BCFZ/BCFS) → `services/gpifImport.ts`. MIDI (lazy chunk `midi-import`, loaded by `importSongFile`): `services/import/midiFile.ts` (`parseMidiFile`, the Standard MIDI File reader) → `services/midiImport.ts` (`buildSongFromMidi`: per-quarter straight/triplet grid, held notes to voice 2). MusicXML (`.musicxml`/`.xml`/`.mxl`, partwise and timewise): `services/musicXmlImport.ts`, a lazy chunk (`parseMusicXml` → `applyGpifSong`). Readers report what they drop with `warnImport` (`services/importWarnings.ts`; one banner after loading); pickup bars become a short first bar (`import/pickupBar.ts`). Real files from other programs: `e2e/fixtures/files/real/` (`SOURCES.md`), pinned by `tests/realFiles.test.ts` (Vitest, the full import path in jsdom). Example songs (File → Example songs, phone menu, first-run card): catalog `data/exampleSongs.ts`, MIDI in `public/examples/` (Mutopia, public domain/CC; credits there and in `CREDITS.md`), loader `services/exampleSongs.ts`, dialog `ExampleSongsModal.vue`; band songs written in code (`data/demoArrangement.ts`, `data/exampleShuffle.ts`) build on `data/songBuilder.ts`. Exports (lazy `songExport` chunk): `musicXmlExport.ts`, `midiExport.ts` (`buildMidiFile(source, { unrollRepeats })`), `gpifExport.ts` + `gpxWriter.ts` (GPX and GP7/8 `.gp`, a stored ZIP), `gp5Export.ts` (`writeGp5(source)`, `currentSongAsGp5()`), `.gt` (`utils/gtSerialization.ts`). Parsers build plain data first and then apply it (`parseGpif` → `applyGpifSong`, `parseGuitarPro` → `applyGuitarProSong`), which keeps them testable in node: `tests/guitarProImport.test.ts` pins GP3/GP4 (files built byte by byte in `tests/helpers/guitarProBytes.ts`, there are no real ones in the repo) and the GP5 showcase against JSON snapshots in `tests/__snapshots__/guitarPro/`, plus a GP5 write → read roundtrip.

**Notation, print, practice (Big wins 13–14, 24).** Bar keys are `measureMeta.keySignature` (fifths, on every bar) + `keyMinor`; `utils/keySignature.ts`, spelling and bar accidentals `utils/pitchSpelling.ts`; the tab layout reserves the staff's key signature room (`keySignatureRoom` in `utils/measureBeatLayout.ts`, row starts in `measureLayoutEngine.ts`). Clefs: `track.clefs` (bar -> clef, `utils/clefs.ts`, Clef dialog, one undo step via `recordTrackEdit`); slash beats `beat.slash` (`toggleSlashBeats`); the view options rhythm on stems and multi-bar rests (`utils/multiRests.ts`; hidden bars have width 0, read widths with `renderedMeasureWidth`) sit in the toolbar's "Tab view options" menu. Printing: `services/printView.ts` (whole rows per A4 page, also used by the PDF export). Practice: section loops from sequencer markers (`services/sectionLoops.ts`, also `loopBars`, and per-section trainer speeds in `stores/sectionPracticeState.ts`), the fretboard/keyboard dock under the tab (`components/practice/PracticeDock.vue`, `services/practiceDock.ts`), A/B loop handles on the tab (`moveRangeEdge`), the options in `PracticeOptions.vue` (popover and `DIALOGS.PRACTICE`), per-song speed/loop memory (`services/practiceMemory.ts`, also a seventh `.gt` part), big beat counter (`stores/beatClockState.ts`, `BigBeatDisplay.vue`), tuner (`services/audio/tuner.ts`, lazy, microphone only while its dialog is open).

**Layouts.** `stores/layoutModeState.ts`: under 900 px a compact phone layout (`components/compact/`: `CompactBar`, `TouchNotePad`; the desktop toolbar `Menu.vue` is not mounted, the sequencer, effects bar and footer stay mounted but hidden; the song file input and the note menu live in `App.vue` for both), 900–1199 px desktop chrome with the sheet fitted to the window, wider the fixed desktop sheet. Sheet fitting: `services/compactLayout.ts`. Touch on the tab is one pointer pipeline, `services/touchGestures.ts` (pure `classifyGesture`: pinch, swipe = next/previous beat while editing, long-press = note menu). Phone dialogs are bottom sheets (`compact.css`; `BaseModal` doesn't drag them); graph editors use pointer events in viewBox units (`utils/svgPoint.ts`). The guitar neck is `components/Fretboard.vue` (guitar dialog; the phone pad's fretboard input, `placeNoteOnString`); neck frets count from the nut incl. capo, tab frets from the capo (`utils/fretboard.ts`). `?layout=compact|desktop` forces a layout.

**The site around the app (Big win 34).** `index.html` has a static intro inside `#app` (replaced on mount), `<noscript>` and JSON-LD; keep its `<!-- site:head -->` marker. Help and search pages (`getting-started.html` with the shortcut list generated from `SHORTCUTS`, three search pages, an English `privacy.html`), `robots.txt` and `sitemap.xml` are generated from `site/` by `site/vitePlugin.ts` (also served by the dev server); add a page in `site/pages.ts` + `site/pages/<slug>.html`. They use `public/legal.css`; the German Impressum/Datenschutz stay hand-written in `public/`. "What's new": `CHANGELOG.md` (user-facing; a new `##` heading per release is what triggers the dialog once for returning users), `services/whatsNew.ts`, `WhatsNewModal.vue`.

**Startup and bundle.** `App.vue` → `startUp()` in `services/startup.ts` (first visit loads the demo song from `data/demoArrangement.ts`; e2e uses the small riff in `data/demoSong.ts`). Chunks are assigned in `vite.config.ts` (`MODULE_CHUNKS`, `EDITOR_CORE_PATHS`, `manualChunks`; Rollup pulls a named chunk's unassigned dependencies into it, so shared startup code needs a named chunk) and each has a size budget in `scripts/check-bundle-budget.mjs` (entry 16 KB, `toolbar` = `Menu.vue` 32 KB, `editor-core` 240 KB, 228 used after Big win 30 (the script counts KiB, Vite prints kB: 233 kB); startup set 471 of 500 KB). `editor-core` holds the editor, playback/audio and stores together because they import each other (the dialog handlers, `dialog-handlers`, and the Guitar Pro readers, `gp-import`, were split off in Big win 30 by reaching them only through `import()`): two chunks that import each other crash only the production build ("Cannot access 'x' before initialization"; the dev server is fine), and `check:bundle` fails on such cycles. New startup code should be lazy or go into a named chunk; check `npm run build:check` and `vite preview` after moving modules between chunks. `check:bundle` also fails when the startup set (entry + static imports) passes 500 KB or contains a chunk listed as lazy (`LAZY_CHUNKS`). The dialogs mount when first opened (`ModalsContainer`, one async chunk per dialog, `dialog-shell` for `BaseModal`); vanilla-picker loads with the track settings dialog. Measure before optimizing: opening a 140-bar GP5 spent 2 % in parsing and 70 % in serializing the song through the reactive proxy (now `toRaw`, HANDOVER 3.42), so a Web Worker for import was not worth it.

## Tests

- **Vitest runs in `node`.** Opt into a DOM per file: `// @vitest-environment happy-dom` (components), `// @vitest-environment jsdom` (XML: happy-dom rejects CDATA). Legacy singletons that need a browser are mocked only where a file opts in, with the one-line `vi.mock(..., () => import('./helpers/legacyMocks').then(...))` pattern (see `tests/helpers/legacyMocks.ts`). Mock `Song` with `tests/helpers/songMock.ts`. `tests/playbackScheduler.test.ts` shows how to drive the real scheduler on fake timers; `tests/playbackCharacterization.test.ts` logs everything playback does per scenario (file snapshots in `tests/__snapshots__/playback/`).
- **E2E tests drive the app through its own modules**: `await import('/src/stores/song.ts')` inside `page.evaluate` (works because Playwright runs against the Vite dev server). Song `notes` arrays are sparse; use `Array.from(notes, …)`, not `.map`.
- `waitForEditorShell(page)` (`e2e/helpers.ts`) loads the small one-track riff (frets 0, 2, 3, so assert other frets); `{ demo: 'arrangement' }` gives the four-track demo. It waits for `html[data-editor-ready]`; tests that play audio also call `waitForSoundFont(page)` (`data-soundfont-ready`). No `networkidle` waits.
- Phone tests are `e2e/*.mobile.spec.ts` (run only in the `mobile` project). Long songs: `growSong()` or the effects fixture (`e2e/fixtures/effectsShowcase.ts`) with the overlap detector, never the user's GP5 file.
- Screenshot baselines (`e2e/classical-notation.spec.ts-snapshots/`, `e2e/visual*.spec.ts-snapshots/`) are committed for `win32` only (local runs); CI compares with the base commit instead (see Commands). Every screenshot test carries the tag `@visual` (CI selects them with it). Refresh after an intended visual change with `--update-snapshots`; a change under the 1 % `maxDiffPixelRatio` passes and is *not* rewritten, so delete that baseline file to regenerate it.
- For visual checks write throwaway specs as `e2e/zz-*.spec.ts`, pass the output folder via an env var, and delete them afterwards.

## Code style

- TypeScript: no semicolons (Prettier). `.vue` files aren't formatted by Prettier yet; match the file you're in. Short comments that explain *why*.
- Toolbar popovers must `Teleport` to `<body>` (`#completeBar` clips overflow).
- **Icons:** `<AppIcon name="…" />` (`components/AppIcon.vue`, names typed from the generated `src/assets/icons/icons.ts`). Add an icon by putting an SVG into `src/assets/icons/source/` and running `npm run icons`; draw it in one dark colour (it becomes `currentColor`). No `<img>` icons and no filters for dark mode; instrument illustrations in `public/instrumentIcons` are the exception.
- **Colours come from `src/assets/css/tokens.css` only** (`tests/designTokens.test.ts` fails on literals elsewhere, in styles, templates and TS). Use the semantic tokens (`--color-*`, `--tab-*`, `--editor-*`, `--seq-*`); their dark values are under `#darkMode` there, so components need no dark-mode rules. In SVG markup set colours as `style="fill: var(--…)"` (attributes can't take `var()`). A token defined from another themed token must be declared on `:root, #darkMode` (see the block at the end of tokens.css).
