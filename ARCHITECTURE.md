# GuitarTab architecture

How the editor is put together as of October 2026, after the core port (HANDOVER 3.28–3.34) moved the last of the old `src/assets/js` code into typed modules. This file describes the current code; how it got here is in `HANDOVER.md`, the working plan in `../IMPROVEMENTS_AUDIT.md`, and the short version for day-to-day work in `CLAUDE.md`.

## Overview

GuitarTab is a browser editor and player for guitar tablature: Vue 3, TypeScript and Vite, Web Audio for sound, VexFlow 4 for standard notation. It opens Guitar Pro 3–8, MusicXML, MIDI and its own `.gt` files and writes `.gt`, GP5, GPX, MusicXML, MIDI, PDF and SVG.

There is no framework beyond Vue: no Pinia, no router. Application state is plain `reactive` modules in `src/stores/`, the logic lives in `src/services/`, and Vue components render and forward user input.

## Folders and layers

```
src/
  main.ts, App.vue    app shell: mounts Vue, lays out the regions, starts the editor
  components/         Vue: toolbar (Menu.vue), tab renderer (tab/), dialogs (*Modal.vue),
                      studio panels (Mixer, Equalizer, Compressor, audio/), phone UI (compact/)
  composables/        functions used in component setup (layout, selection, viewport, toolbar state)
  services/           the application logic, no Vue components
    editor/           editing commands, undo, layout engine, selection, keyboard, note entry
    playback/         song cursor, scheduler, playhead
    audio/            audio graph, sample player, SoundFont, drums, metronome, meters
    dialogs/          dialog ids and open/close (dialogs.ts), the lazy handler registry and handlers
    notation/         classical notation (VexFlow), lazy
    import/, *Import.ts, *Export.ts   file formats
    midi/             MIDI input devices, live input, placing pitches on strings
  stores/             reactive state modules (song, selection, settings, layout, practice...)
  utils/              pure helpers (durations, tab geometry, lanes, event bus, shortcuts table)
  types/              the song model and renderer types
  data/               instrument tables, the demo songs
```

Imports go downwards: `components` → `composables` → `services` → `stores`/`utils`/`types`/`data`. The lower layers (`services`, `stores`, `utils`, `types`, `data`) must not import components or composables; ESLint (`no-restricted-imports` in `eslint.config.mjs`) and `tests/layering.test.ts` enforce it, and the test also checks that `src/assets/js` stays gone. Module-level reactive state belongs in `stores/`, not in `composables/`.

Inside `services/` the layering is not strict. The editor, playback and audio call each other in both directions (playback reads the stores and the layout, edits restart playback). That is why they share one bundle chunk (see [Bundle](#bundle)). Dialog handlers and the Guitar Pro readers depend on the editor, but the editor reaches them only through `import()` (`dialogs/dialogs.ts`, `songImport`'s lazy readers), so they are lazy chunks.

## Startup

1. `main.ts` loads the global styles (`assets/css/guitarTab.scss`, `style.css`, `assets/css/compact.css`) and mounts `App.vue`. `style.css` defines CSS variables the tab renderer needs; without it the sheet and string lines are invisible.
2. `App.vue` renders the toolbar (`Menu.vue`, desktop and tablet only; phones get `CompactBar` and never mount it), the song file input, and the tab (`GuitarTabView.vue`) right away and loads the rest lazily with `defineAsyncComponent`: effects bar, sequencer, footer, drafts panel, help overlays, the note menu and the phone UI. Cloud songs (`?song=<id>`) and the phone sheet fitting are dynamic imports too. No dialog is mounted at startup: `ModalsContainer.vue` mounts with the first dialog that opens, and each dialog component (its own async chunk) mounts the first time it is shown (`dialogState.mounted`) and stays mounted afterwards.
3. On mount it calls `startUp()` (`services/startup.ts`): document listeners (shortcuts in the capture phase, Ctrl + wheel zoom, unlocking audio on the first gesture), `playback.init()`, an empty song, the audio buses, then the first song. A first visit loads the four-track demo (`data/demoArrangement.ts`, its own lazy chunk); e2e tests ask for the small riff in `data/demoSong.ts`. The SoundFont loads in the background.
4. `songAutosave.ts` offers the newest unsaved snapshot for recovery.
5. Readiness is published as `<html data-editor-ready>` and `data-soundfont-ready` (`utils/startupReadiness.ts`); the e2e helpers wait for them.

## The song model

`types/song.ts` defines the model. A song is `measures[track][block][voice][beat]`: a *block* is a bar, and each entry is a `Beat` with its duration, effects and a sparse `notes` array indexed by string. Bar-level data (time signature, repeats, voltas, markers, tempo changes, navigation signs) is in `measureMeta[block]`. Tracks, tuning, chord libraries (`chordsMap`), mixer channels (`allChannels`) and per-track playback settings (`playBackInstrument`) sit next to it. Optional features are optional fields (`beat.text`, `beat.chord`, `beat.lyrics`, `effects.stroke`, …).

**Navigation signs** are `measureMeta[block].directionTargets` (Segno, Segno Segno, Coda, Double Coda, Fine: where jumps go) and `directionJumps` (D.C./D.S./D.S.S., each plain, al Coda, al Double Coda or al Fine, and "To Coda"/"To Double Coda", taken at the bar end), with Guitar Pro's GPIF names. `utils/directions.ts` has the lists (in GP5 header order), the labels and `jumpRule` (where a jump goes and what playback looks for afterwards). They are drawn in the `direction` lane (`TabMeasureInfo.vue`), edited in the Navigation signs dialog (Bar tab), read from GP5 (the 19 bar numbers in the header) and GPIF (`<Directions>`), and written to GP5, GPX and MusicXML (`<segno/>`, `<coda/>`, `<words>` with `<sound dalsegno/dacapo/tocoda/fine>`).

**Key signatures** are `measureMeta[block].keySignature` (fifths, −7…7, 0 = C; every bar carries the key in effect, like the time signature) and `keyMinor` (optional). Helpers: `utils/keySignature.ts` (`keyFifths`, `keyChanges`, names, VexFlow's key spec). Read from GP3–5 (song key + bar headers), GPIF (`<Key>`) and MusicXML (`<key>`, carried on), written to all three; edited in the Key signature dialog (Bar tab, `KeySignatureModalHandler`: from the cursor's bar to the next change, all tracks, one undo step). Old `.gt` files whose bars all say −1 (the former default) are migrated to C.

**Lyrics** are `beat.lyrics[verse]`, one syllable per note beat and verse (up to five verses, as in Guitar Pro); a syllable ending in `-` joins the next one. `utils/lyrics.ts` is the pure core: the Guitar Pro lyric text form (spaces separate, `-` hyphenates, `+` joins words on one beat, `[…]` comments, each extra space skips a note) parsed and written back, flowing syllables over the note beats from a bar on (`flowLyrics`, `applyLyricLines`) and collecting them again (`collectLyricLines`). Rests never take a syllable.

- `stores/songState.ts` holds that data as one `reactive` object; it is the single source of truth.
- `stores/song.ts` exports `Song`, a `Proxy` over `songState` that adds accessors (`findBeat`, `getBeat`, `getNote`, …) and default objects. Reads and writes go straight to `songState`, so `Song.measures[...] = ...` is reactive. Prefer the accessors over indexing by hand, and `toRaw` for bulk reads.
- **String order:** string index 0 is the *lowest* string (pitch = tuning + fret), drawn on the bottom tab line. `stringLine()` in `utils/tabStrings.ts` converts a string index to a screen line. The exception is chord `frets[]`, stored highest string first.
- Durations are in ticks (whole note = 64), `utils/duration.ts`. Tuplet group ids and fill counters are `stores/tupletState.ts`.
- `.gt` files and autosave drafts from older versions are upgraded on load by `services/songMigrations.ts`; changing a field means adding a migration step there.

## Rendering the tab

```
GuitarTabView.vue
  └ useGuitarTabLayout ── editorCore.buildModernTabRows ── measureLayoutEngine
        │                                                    ├ writes stores/tabLayoutState (blockToRow, blocksPerRow, measureOffset...)
        │                                                    └ caches per block in stores/tabRenderLayout
        └ useVisibleTabRows → TabRow.vue (mounted rows only)
              └ TabMeasure / TabNote / TabDurations / TabEffects / TabMeasureInfo / ChordDiagram
          ClassicalNotationLayer.vue → ClassicalRowSurface.vue (one VexFlow staff per visible row)
```

- `services/editor/measureLayoutEngine.ts` is the only row-breaking and bar-width pipeline (`computeBarWidth`, `relayoutTrack`, `barWidthChangesRows`). The plain arrays it writes to `tabLayoutState` are what playback, scrolling and navigation read. `redrawTrack` (`layoutInvalidation.ts`) lays a track out again.
- Vertical layout is per row: `utils/tabRowLanes.ts` stacks annotation lanes (effects, text, chords, dynamics, lyrics — the lowest, one line per verse) above and below the strings, in row-local coordinates with `y = 0` at the top string. Horizontal beat positions come from `utils/beatPositionInRow.ts`, `utils/measureBeatLayout.ts` and `services/editor/beatGrouping.ts`. Two view options change the layout: rhythm on stems (`Settings.tabRhythmOnStems`; voice 1 stems go up into a `rhythm` lane above the strings in two-voice bars) and multi-bar rests (`Settings.multiBarRests`, `utils/multiRests.ts`: a run of empty bars is drawn as its first bar, the others are `hidden` with width 0 but still there for playback and the cursor; read measure widths with `renderedMeasureWidth`).
- The layout is computed inside a `computed` that writes reactive state; reads during that write use `toRaw`, otherwise Vue reports "Maximum recursive updates". The bar scans (`computeBarWidth`, `groupMeasureBeats`, the lanes' beats) read the song raw too: tracking every beat as a dependency cost 3–4× the layout itself (Big win 25), and the computed re-runs on every edit anyway (`songDataVersion`, `renderVersion`). The rows still hand the reactive bars to their components.
- **Score view** (`Settings.scoreView`, Big win 25): the shown tracks stacked per system. `computeTrackLayout` is one track's pass: `beginTrackLayout` measures the bars, `breakIntoRows` breaks them, `layoutRow` lays out a row at a given top, `finish` stores it. `services/editor/scoreLayout.ts` runs one pass per shown track, breaks rows once over each bar's widest width and lays each system out staff by staff (`SCORE_STAFF_GAP`, `SCORE_SYSTEM_GAP`), so every track has the same rows and bar x/widths (beats spread over the shared width) while keeping its own lanes. Rows carry `trackId`/`voiceId` (the edited track in its edited voice, the others in voice 1) and `lowerStaff` (no bar numbers, tempo, markers, voltas or signs below a system's top staff). `editorCore.buildModernTabRows` and `computeTrackLayoutFromSong` (so `relayoutTrack`/`redrawTrack`) switch to it when `scoreTrackIds()` is set; `barWidthChangesRows` lays the score out again and compares the edited track's rows. The edited track stays `Song.currentTrackId`: a click in another staff, or Alt+↑/↓ (`moveCursorToTrack` in `scoreViewCommands.ts`; without the score view it walks all tracks), switches to that track, so every edit command works unchanged. `GuitarTabView` draws the track names in the page margin and a bracket per system, and the playhead across the whole system; print pages break between systems (`scoreSystems`). The tracks shown are `stores/scoreViewState.ts` (null = all, reset on load and track deletion), chosen in the Tab view options menu. Classical notation and the score view exclude each other (`setScoreView`, `toggleClassicalNotation`), and multi-bar rests are off in it.
- Only rows near the viewport are mounted (`useVisibleTabRows`, `stores/tabVirtualizationState.ts`). Anything that needs the whole tab in the DOM (PDF/SVG export, printing) wraps the work in `withAllRowsRendered()`.
- Re-rendering after an edit goes through version counters (`stores/renderVersionState.ts`, Big win 30; they replaced seven `render.*` events): `song` (the tab layout computed in `useGuitarTabLayout` reads it), `bars['track:bar']` (bumped for exactly the bars an edit changed) and `chords` (the chord library; the chord manager watches it). Commands bump them through `services/editor/renderCommands.ts` (`requestBlocksRender`, `requestFullRender`, …), and `recordBarEdit` bumps the changed bars on every edit, undo and redo. The per-bar counters are there for components that want one bar's changes; the row layout still re-runs as a whole (cheap since 3.50) and the per-block render cache decides what redraws.
- **Key signatures on the staff:** `utils/pitchSpelling.ts` spells each pitch in the bar's key (scale notes keep the key's spelling, others are sharpened in sharp keys and C, flattened in flat keys) and `BarAccidentals` decides which accidentals a bar shows (once per line and bar, naturals against the key, none on tied notes). The staff draws the key at the song start, at changes (with cancelling naturals) and at every row start. The room for it is reserved in the tab layout, so tab digits and note heads stay aligned: `keySignatureRoom` (`utils/measureBeatLayout.ts`) is part of `barLeftOffset` and `computeBarWidth`, and the row breaker adds the row-start part to the first bar of each row (`rowStartRoom` in `measureLayoutEngine.ts`). Without the classical view, for drums and in C it is 0.
- **Tied notes** show only their tie arc, or their fret in parentheses with `Settings.tiedNotesInParentheses` (View toolbar, `TabNote.vue`).
- **Classical notation** (`services/notation/`) is loaded only when switched on. `classicalNotationAdapter.ts` loads it; `classicalNotationLifecycle.ts` documents the activation order; `vexflowNotes.ts` converts beats to VexFlow notes (pure) and `classicalNotation.ts` draws. The staves are laid out from metrics computed from the notation data (`stores/classicalNotationLayoutState.ts`, whose `active` means "metrics are ready"), never from drawn output, so tab and staff rows line up. The installed `@types/vexflow` describe VexFlow 1.2; check new calls against `node_modules/vexflow/build/types`. Clefs come from `utils/clefs.ts` (`track.clefs`: bar -> clef from there on; else by instrument), per bar in the conversion and drawn at row starts and changes; slash beats (`beat.slash`) become slash heads on the middle line.
- **Layouts** (`stores/layoutModeState.ts`): under 900 px the phone layout (`components/compact/`: `CompactBar`, `TouchNotePad`), from 900 px the desktop chrome with the sheet fitted to the window, from 1200 px the fixed desktop sheet. In the phone layout the desktop chrome stays mounted but hidden, because some code still finds elements by id. Sheet fitting: `services/compactLayout.ts`. `?layout=compact|desktop` forces one. Touch on the tab goes through one pointer pipeline, `services/touchGestures.ts` (pure `classifyGesture`): pinch zooms, a sideways swipe moves the cursor a beat while editing, a long-press opens the note menu; vertical panning stays native scrolling. On a phone dialogs are bottom sheets that `BaseModal` doesn't drag, and the graph editors (bend, tremolo bar) use pointer events in viewBox units (`utils/svgPoint.ts`) so they work scaled down and with a finger. The note pad enters frets on a number grid or on the fretboard (`Settings.touchFretboard`).

**Look.** Colours come only from `assets/css/tokens.css`: primitive ramps and semantic tokens (`--color-*`, `--tab-*`, `--editor-*`, `--seq-*`), dark values under `#darkMode` (the id on `<body>`, kept in step with `Settings.darkMode` by `services/theme.ts`), so components need no dark-mode rules; `tests/designTokens.test.ts` fails on colour literals anywhere else. Icons are one set: SVGs in `assets/icons/source/` turned by `npm run icons` into `assets/icons/icons.ts`, drawn by `components/AppIcon.vue` in `currentColor`. Toolbar styles are `assets/css/toolbar.css`.

## Editing

**Selection.** The edit cursor (one string of one beat) and the two ends of the range selection are `stores/selectionState.ts`. `services/editor/rangeSelection.ts` drives the range (`startRange`, `extendRange`, `clearRange`, `notesInRange`) and also owns the playback loop, since the selected range is the loop. Clicking in the tab or the sequencer moves the cursor through `navigation.setClickedPos`.

**Commands and undo.** Every undoable change is an `EditCommand` on the single history in `services/editor/editCommands.ts` (`undoHistory`, a bounded `revertStack.ts`; reactive `undoAvailability` for the buttons). Most edits go through `recordBarEdit(label, scope, mutate)`: it snapshots the affected bars before and after `mutate` and records one step, so no edit needs a hand-written inverse. It restores bars in place (references to beats and notes stay valid), rolls back when `mutate` returns `false` or throws, and nests: low-level mutators (`setFret`, `deleteNote`, `changeNoteDuration`) record themselves, and a caller that wraps several in `recordBarEdit`/`editTransaction` gets one step. The other command families:

| Area | Module |
|---|---|
| frets, notes | `noteCommands.ts`, note entry at the cursor in `noteEntry.ts` |
| note lengths, tuplets | `durationEditing.ts`, `durationCommands.ts`, `durationModifierCommands.ts` |
| rests, tuplet numbering, track refresh | `barFilling.ts` |
| bars added/removed | `measureStructureCommands.ts` |
| time signatures | `timeSignatureCommands.ts` |
| effects on beats, notes and bars | `effectToggles.ts`, `notationCommands.ts`, `dynamicsCommands.ts`, `services/menuEffectMutations.ts` |
| song tempo, track volume, chord library, track settings | `songSettingsCommands.ts` (`recordTrackEdit`), `recordSongInfoEdit` |
| copy, cut and paste | `clipboard.ts` (copies are snapshots; without a range they take the cursor's beat and paste from the cursor on; `pasteAsNewBars`) |
| bars inserted in the middle | `insertBars` in `measureStructureCommands.ts` (shifts `tiedTo` and automations; one command, so it nests in a paste) |
| rhythm keys: dot, tuplet, tie, insert/delete beat | `rhythmCommands.ts` (lazy `editing-tools` chunk); rest at the cursor: `makeRestAtCursor` in `noteEntry.ts` |
| keyboard selection, transpose | `selectionCommands.ts` (lazy), placing transposed notes on strings: `utils/transpose.ts` |
| zoom | `zoom.ts` (`Settings.currentZoom` is the only zoom value) |

Every command re-renders, refreshes the toolbar and emits `song-data-changed`, which triggers autosave. Some changes deliberately have no undo: mute, solo, pan, effect knobs, master volume, the studio panels.

**Keyboard.** All shortcuts are one table, `utils/keyboardShortcuts.ts` (`SHORTCUTS`), dispatched by `handleKeyDown` in `services/editor/keyboardDispatch.ts`. The Help sheet is generated from the same table, grouped in table order (Enter notes, Move, Select, Note length, Rhythm, Playback, Edit, View). Letters and digits match on `event.code`, so they work on any layout (and synthetic events without a `code` don't trigger them). Selection: Shift+←/→ and Shift+click extend a range from the cursor (the range is also the loop), Ctrl+A selects the bar and again the track. Rhythm: `.` dot, Alt+3/5/6/7/9 tuplet, R rest, L tie, Insert / Ctrl+Delete insert or delete a beat inside the bar (an insert only takes room from the rests the bar ends with, so notes are never pushed out). Alt+1/2 voices, Alt+↑/↓ the previous/next track (in the score view the staff above/below), Ctrl+(Shift+)↑/↓ transpose. The handlers for the lazy `editing-tools` commands take the key at once and run the command when the chunk has loaded.

**Voices and short bars.** The voice being edited is drawn as before; voice 2's frets use `--tab-voice2`, and the other voice's notes are drawn faintly over it (`utils/otherVoiceNotes.ts`, placed by time in the edited voice's beats, with a halo in `--tab-bg` so they read over rests; hidden where the edited voice has a note at the same place). A click on a faint note edits that voice there (`otherVoiceNoteAt` on `barOtherVoiceNotes`, in `useTabRangeSelection`); the cursor of voice 2 has a border in `--tab-voice2` and a small "2". Switching voice or track (`switchTrack`) keeps the cursor at the same time in its bar (`beatAtSameTime`) and moves the drawn cursor along. Classical notation draws the other voice on the same staff (`classicalNotation.drawOtherVoice`: stems voice 1 up / voice 2 down, placed by time with `otherVoiceBeatXs`, rests left out, group `vf-other-voice`). Bars that are too short (imported files, deleted beats) get rests at the end: `padBarWithRests` in `barFilling.ts`, on load (`loadSongIntoEditor`) and after the rhythm commands.

**Toolbar.** Every toolbar action is one entry in `services/editor/toolbarActions.ts` (`TOOLBAR_ACTIONS`: element id, label, icon, group, shortcut, `run()`; plus `TOOLBAR_GROUPS` and the edit tabs `EDIT_TABS`). `Menu.vue` renders two bars from it: `#tabBar` for the song and playback (file, undo, transport, practice, the tempo pill, view, help, theme) and `#statusBars`, the edit bar with the tabs Note · Effects · Dynamics · Bar · Text. Pressed and disabled song state comes from a `computed` (`composables/useToolbarState.ts`) over the cursor, the range and the song, so nothing has to tell it to refresh; state that isn't song state (theme, undo availability) is on the action itself. When a bar gets too narrow, groups fold into menus: the pure `fitToolbarGroups` (`utils/toolbarFit.ts`) decides, `composables/useToolbarFit.ts` measures (ResizeObserver). Tooltips include the shortcut (`actionTooltip`, one teleported tooltip from `useToolbarTooltip`). Edit-tab and note-menu UI state: `stores/toolbarUiState.ts`. Popovers and menus teleport to `<body>`.

**Note menu.** `components/toolbar/NoteMenu.vue` opens on a right-click on a note, Shift+F10 or the context-menu key (`openNoteMenuAtCursor`), and on a long-press on a phone. It shows the position, common effects, dynamics, lengths, Bar and Text submenus and copy/paste/delete, all taken from the action registry, so it runs the same commands and shows the same states as the toolbar. It is a popover on desktop and a bottom sheet in the phone layout. Note effects and dynamics run through `services/editor/noteEffectCommands.ts`.

**Lyrics entry.** Shift+L (or Text ▸ Lyrics) opens `components/tab/LyricsEntryField.vue`, an input teleported over the lyrics line of the cursor's beat (it follows the cursor each frame; `TabRow` puts the line's offset on the cursor as `data-lyrics-dy`). Space, Tab or a syllable ending in `-` stores it and moves to the next note; a typed or pasted line flows over the following notes; Shift+Tab/Backspace go back, ↑/↓ change the verse, Enter/Escape close. The logic is `services/editor/lyricsEntry.ts` (each stored entry is one `recordBarEdit` step), state is `stores/lyricsEntryState.ts`. The field is loaded with the app, not lazily, so the keys typed right after Shift+L can't reach the sheet first.

**Dialogs** (Big win 30). A dialog window is state: `stores/dialogState.ts` holds the open windows in stacking order (`showDialog`, `hideDialog`, `bringDialogToFront`, `frontDialogId`, `dialogZIndex`) and the dialogs mounted so far. Editor code opens one with `openDialog(DIALOGS.X, params)` / `toggleDialog` (`services/dialogs/dialogs.ts`: every dialog's id and footer name); that loads the handler registry (`dialogHandlers.ts`, the lazy `dialog-handlers` chunk) and calls the handler's `openModal(params)`, which fills its reactive state from the song and shows the window. `BaseModal.vue` renders a window from the store (`active` class, z-index, position), drags it by the title bar and resizes it by its edges with pointer events (`resize="x"` or `"xy"`; not on phones, where windows are bottom sheets), centres it on opening, keeps it on screen when it grows, and moves the focus in and back. `ModalsContainer.vue` mounts each dialog component (an async chunk) the first time it opens and handles Escape. The footer lists the open windows from the store. Handlers never touch the DOM: the Vue component reads and writes the handler's reactive state (`form`, `editor.points`, …) and calls its methods (`apply()`, `submit()`, `confirm()`); dialog components get their handler with `getDialogHandler(id)` (they are lazy, so they import the registry directly). Simple edit dialogs are a config for the generic `EditModalHandler` (`effectModals.ts`: `defaults`/`read`/`scope`/`write`); `handler.apply()` records one undo step, re-renders and closes. Bend, tremolo bar, time signature, chords and track settings (with the tuning) have their own handlers; dialogs whose component does everything use `definePlainModal(DIALOGS.X)`. The master EQ and compressor are audio services (`services/audio/masterEqualizer.ts`, `masterCompressor.ts`): `audioGraph.createBusses()` wires them, the Equalizer and Compressor panels edit them (the EQ graph's drawing is `components/audio/equalizerGraph.ts`; the meters loop hands it the spectrum through `masterEqualizer.spectrumListener` while it is open).

**Accessibility** (audit Big win 10, `services/a11y/`). Dialogs are `role="dialog"` windows named by their title (`BaseModal.vue`), not modals: several can be open. `services/a11y/dialogFocus.ts` (in the lazy `dialog-shell` chunk with `BaseModal`) moves the focus in (the first text field on desktop, else the window), back to where it came from on closing, closes the window in front on Escape (`ModalsContainer`'s document listener, bubble phase, so popovers and fields that take Escape win), and keeps Tab inside it except in the tool windows (piano, guitar, mixers, EQ, compressor, MIDI). Screen readers hear `announce(text)` (`stores/announcerState.ts`) through the hidden live region `#screenReaderAnnouncer` in `App.vue`: undo/redo labels from `undoHistory`, and the cursor and range from `services/a11y/cursorAnnouncer.ts` (lazy, started by `startup.ts`; "Bar 3, beat 2, string 5, fret 7", 120 ms after the cursor stops). Toolbars with `data-roving-toolbar` (`#tabBar`, the edit bar's tool panel) move with ←/→/Home/End and have one Tab stop per `.toolbar__group` (`components/toolbar/rovingToolbar.ts`); `keyboardDispatch` leaves those keys alone only on a button with `:focus-visible` (`isToolbarNavigationKey` in `utils/keyboardShortcuts.ts`), so arrows after a mouse click still move the tab cursor. Landmarks: `#completeBar` banner, `#mainContent` main, the bottom bars a region, the footer contentinfo. `prefers-reduced-motion` ends every transition/animation (`style.css`). Checks: `tests/tokenContrast.test.ts` (WCAG ratios of the semantic tokens, both themes) and `e2e/accessibility.spec.ts` / `accessibility.mobile.spec.ts` (axe-core on the editor, dark mode, every dialog, note menu, shortcut sheet, phone layout; plus focus, toolbar keys, announcements).

## Playback and audio

```
playback (services/playback/index.ts)        togglePlayback, start/stop, jumpToBeat, setPlayPosition...
  ├ playOrder.ts     pure: the order bars play in (repeats, voltas, D.C./D.S./Coda/Fine), one step or unrolled
  ├ songCursor.ts    pure: the bar sequence the scheduler follows (play order + loop), the next beat of each voice
  ├ scheduler.ts     ticked every 25 ms by timerWorker.ts; schedules beats 0.4 s ahead on the AudioContext clock;
  │                  metronome, count-in, speed trainer, jumps
  ├ notePlayback.ts  how a beat sounds: mute/solo, ties, strums, grace and ghost notes
  ├ playhead.ts      animation loop: playhead position, scrolling, the piano/guitar views
  └ startPosition.ts where Play starts
audio (services/audio/)
  ├ audioGraph.ts    the AudioContext (passed in), track and drum buses, master chain
  ├ masterEqualizer.ts, masterCompressor.ts   master EQ bands and limiter settings (localStorage)
  ├ samplePlayer.ts  playFret/playPitch: SoundFont notes with their effects (bends, slides, vibrato...)
  ├ soundFont/       RIFF/SF2 parser, banks, loader, envelope.ts, sf3.ts (GeneralUser GS, 32 MB; SF3 decoding)
  ├ effects.ts       per-bus chorus and Freeverb
  ├ ampModel.ts      which tracks use the amp simulation, defaults, GP tone-name hints
  ├ ampSimulator.ts  amp + cabinet DSP (lazy chunk amp-sim)
  └ drumKit.ts, metronome.ts, meters.ts
```

**Play order.** `nextPlayedBar` in `playOrder.ts` is one step from a `PlayedBar` (bar, repeat pass, the mode after a D.C./D.S. jump, jumps taken). The rules follow printed music: each jump once; after a D.C./D.S. no repeats and the last volta; "To Coda" only after "… al Coda", Fine only after "… al Fine". The scheduler's `BarSequence` (`songCursor.ts`) fills a ring buffer a few bars ahead with these steps and puts the loop on top (after the loop's end bar comes its start bar, same pass). Jumps and Play start the order afresh at a bar (first pass, no jump taken). `buildPlayOrder` unrolls a whole song (tests, MIDI export). The beat after a scheduled beat (where a slide goes, what a tie extends into) comes from this sequence, so it is right after repeats, voltas, jumps and loops.

**Playhead.** When a beat starts sounding the playhead stands on its digits, which `TabNote` draws at `beatNoteOffset` into the beat's column (`utils/measureBeatLayout.ts`: centred for quarters and shorter, a quarter's half-width in for longer notes, so a half note doesn't sit a quarter late; digits, stems, effects, chords, the cursor, the other voice and classical note heads all use it) (`renderBridge.getPlayheadXInRow`), and glides linearly towards the next beat's digits over the beat's length (`playbackController.movePlayBackBarToPosition`, resolved in `playbackPositionResolver.ts`).

**How a SoundFont note sounds.** The bank is GeneralUser GS (`public/audio/GeneralUser-GS.sf2`, free licence next to it); `?soundfont=musescore` loads MuseScore_General (SF3) instead, for comparison (`soundFontUrl` in `soundFont/loader.ts`). `buildBanks`/`buildBanksFrom` (`soundFont/synth.ts`) lists every zone of a preset per key: all instrument zones, global zones merged in, preset generators added as offsets, key and velocity ranges intersected. `noteOn(program, key, velocity)` returns one voice per zone that covers the velocity (`voicesFor`), so stereo halves and stacked layers sound together, each with its own pan; the velocity comes from the beat's dynamic (ghost notes softer, `velocityOf` in `samplePlayer.ts`). `soundFont/envelope.ts` turns a voice into Web Audio automation: volume attack, hold, a decay that falls in dB to the sustain level, and the zone's release (15 ms–2 s) after the note's length; a low-pass filter with its modulation envelope when the zone uses one (also darker at low velocity, the SF2 default modulator); the modulation envelope to pitch and both LFOs (vibrato, modulation LFO to pitch, cutoff and volume) on `source.detune`/`filter.detune`/a tremolo gain, so they never fight the bends and slides on `playbackRate`. A new note on a string chokes the one still ringing there, and drum notes choke their exclusive class (open/closed hi-hat). Track buses (`TrackBus` in `audioGraph.ts`) are input → (amp) → pan → volume → master with the track's reverb and chorus as parallel sends (the mixer knobs); a note adds its zone's own send amounts through `reverbIn`/`chorusIn`, whose pan and volume `setPan`/`setVolume` keep equal to the dry path's.

**Amp and cabinet simulation.** GeneralUser GS's overdrive and distortion guitars (GM 29/30) are thin pre-distorted samples. A track's `amp` (`{ enabled, drive, tone, cabinet }`, optional; absent = `defaultAmp(program)`: on for 29/30, off otherwise) puts `AmpSimulator` (`ampSimulator.ts`, the lazy `amp-sim` chunk, loaded by the first bus that needs it) between the bus input and its pan, and `sf2Target` then plays the clean guitar (27) for 29/30 (`sampleProgram`). The chain is mono: low cut and mid push → drive gain (0–28 dB) → a fixed 4×-oversampled asymmetric tanh curve with a small expander near zero (gates release tails) → DC block, mid scoop, treble shelf and fizz low-pass (tone) → a cabinet `ConvolverNode` → output gain compensated for drive. The cabinet impulse responses (open 1×12, 2×12, closed 4×12) are computed from biquad cascades at the context's rate and normalized to unit gain in 200 Hz–3.2 kHz, so there are no IR files and no licence question. While the amp is on, notes skip their zone's reverb/chorus sends (they would carry the clean signal around it); the mixer sends after the bus volume still apply. Settings change live (`TrackBus.setAmp`, `audioGraph.applyTrackAmp`; parameters glide 10 ms, the route only changes when on/off changes). The sequencer's knob view has an Amp column (`TrackAmpPanel.vue`: on/off, drive, tone, cabinet; previews live through `previewTrackAmp`, records one undo step "Amp settings" on close through `setTrackAmp`). Imports set `amp` from tone names (`ampFromToneNames`): GP5.1's RSE preset name and category ("Hard Rock - Default" / "Distortion Tones"), GP6–8's sound name/label/path and RSE effect ids and chain names. `.gt` keeps it (tracks are saved as JSON); GP5/GPX/MusicXML/MIDI exports don't write it (MIDI keeps the program, so 29/30 stay distorted elsewhere). Changing a track's instrument builds a new track, so its amp goes back to the new program's default.

**SF3.** The parser keeps each compressed sample (sampleType bit 0x10) as its Ogg Vorbis bytes; `soundFont/sf3.ts` decodes them after the download with `decodeAudioData` on an `OfflineAudioContext` at the sample's own rate (no resampling, loop points stay exact), eight at a time, progress as a second loading stage ("Preparing instruments…"). Streams the browser rejects (Chrome: 17 tiny synth-waveform streams of MuseScore_General; a browser without Ogg Vorbis: all) are decoded afterwards by `@wasm-audio-decoders/ogg-vorbis` in a Web Worker, imported lazily (its own `vorbis-decoder` chunk, ~84 KB, only fetched then). A sample neither decoder reads stays empty and its zones are left out (a console warning names it).

**Loading the SoundFont.** `loadSoundFont` reports the download in `stores/soundFontState.ts`; the Play buttons (`Menu.vue`, `CompactBar.vue`) show it as a ring or bar with a label, and Play pressed meanwhile waits (`playWhenReady`; pressed again or Stop cancels) and starts when the load settles (`onSoundFontSettled`, registered in `playback.init`). Without a load (unit tests: status `idle`) or after a failure, Play starts at once.

The song clock counts whole notes; `spw()`/`wps()` in `playback/tempo.ts` convert to seconds and apply the practice speed (`stores/practiceState.ts`). Practice features (speed, metronome, count-in, speed trainer, loop) are the transport in `PracticeControls.vue` over `practiceState` and the scheduler. Section loops: a marker in the sequencer's master row loops its section up to the next marker (`services/sectionLoops.ts`, `utils/markerSections.ts`; through the range selection, so it is the same loop as a dragged one). Practice memory (`services/practiceMemory.ts`): speed and loop per song in `localStorage` (keyed by title, artist, bar and track count, 50 songs) and as a seventh part of `.gt` files and autosave drafts (`withPracticePart`/`practicePartOf` in `gtSerialization.ts`; not song content, so it doesn't make a song unsaved); restored after every load (`recallPractice`). Muted/solo tracks were already saved (`playBackInstrument`). The big beat counter (`BigBeatDisplay.vue`, `practiceState.bigBeat`) shows the beat of the bar during the count-in and playback: the scheduler queues each beat with its audio time (`stores/beatClockState.ts`), the playhead's frame shows it when the clock gets there. The tuner (`TunerModal.vue`, `services/audio/tuner.ts`, lazy chunk `tuner`) listens to the microphone only while open (raw input, no echo cancellation), detects the pitch with YIN (`utils/pitchDetection.ts`) and shows the nearest string of the shown track's tuning. `stores/soundingNotesState.ts` holds the notes the piano and guitar dialogs show as pressed: those playback has reached plus live notes. The guitar neck is `components/Fretboard.vue` (geometry in `utils/fretboard.ts`): the guitar dialog shows sounding notes on it (frets counted from the nut, capo drawn), and the phone note pad uses it in `input` mode (columns counted from the capo; a tap calls `placeNoteOnString` in `services/editor/noteEntry.ts`).

MIDI input: `services/midi/devices.ts` lists and connects devices (access is requested when the MIDI dialog opens); `liveInput.ts` sounds live notes and writes recorded ones (one undo step per flush), placing pitches on strings with `noteArranger.ts`.

## Import and export

- **Import** has one entry point, `importSongBytes(fileName, bytes)` in `services/songImport.ts`, which picks the parser by file ending, throws a typed `ImportError` (`importErrors.ts`) and puts the previous song back when a file can't be read. `importSongFile` loads a reader that is not in the startup bundle first (MusicXML, MIDI) and passes it in; `openSongFile` (the toolbar's file input), `loadGtBytes` (autosave, cloud) and `loadBuiltSong` (demo) build on these.
  - **Import warnings** (`importWarnings.ts`): readers call `warnImport(kind, count)` for what the tab can't hold (notes without a free string, third/fourth voices, overlapping notes in one voice); `importSongBytes` collects them around one import and returns them as phrases, `importSongFile` shows them in one banner ("Opened, but left out …").
  - **Pickup bars** (`import/pickupBar.ts`): the model has no anacrusis flag, so a bar the file marks as a pickup (GPIF `<MasterTrack><Anacrusis/>`, MusicXML first measure `implicit="yes"`) gets a time signature as long as its notes (2/4 before 4/4), as TuxGuitar does.
  - GP3/4/5: `services/import/guitarPro/` (`parseGuitarPro` → `applyGuitarProSong`): one reader for all three versions, `parser.ts` (header, bar headers, tracks, bars) and `beatReader.ts` (beats, chords, effects, notes, mix changes), each taking the major version; every `version` check is one format difference (GP4 adds lyrics and a second effect-flag byte, GP5 page setup, signs, two voices, RSE data; GP5.10 a few fields, `minor`).
  - GP6/7/8: `gpContainers.ts` unpacks the ZIP/BCFZ/BCFS container, `gpifImport.ts` reads the GPIF XML (`parseGpif` → `applyGpifSong`).
  - MIDI (lazy chunk `midi-import`): `import/midiFile.ts` reads the file, `midiImport.ts` builds a song. Positions in 24ths of a quarter; each quarter gets the grid its onsets fit (16ths, triplet 8ths, triplet 16ths, 32nds; one grid for all tracks), whole quarters inside triplet passages are plain quarters. A note still sounding at the next onset goes to voice 2 (bass under arpeggios; not when that would be most of the track, i.e. legato playing). Strings are chosen per onset for both voices together, avoiding strings still ringing, notes with the fewest playable strings first.
  - MusicXML (`.musicxml`, `.xml`, compressed `.mxl`): `musicXmlImport.ts`, a lazy chunk (`parseMusicXml` → `applyGpifSong` in `import/songData.ts`). Timewise scores are turned into partwise first (`timewiseToPartwise`); one track per part, its first two voices. Notes keep `<string>`/`<fret>` when present, else they are placed with `midi/noteArranger.ts` (an octave further in when out of range); notes that don't fit are counted and reported in a banner. Chord symbols (`<harmony>`, shared names in `utils/chordSymbols.ts`) become name-only chords, which the tab draws without a diagram.
  - Parsers produce plain data first and apply it afterwards, so they run in node tests. Files from other programs (alphaTab's test files, Mutopia MIDI) are in `e2e/fixtures/files/real/` (`SOURCES.md`); `tests/realFiles.test.ts` opens each through `importSongFile` and pins a text fingerprint per file.
- **Example songs** (lazy chunk `example-songs`): the catalog `data/exampleSongs.ts` (title, composer, credit and licence, which tracks to keep, transposition), the MIDI files in `public/examples/` (`CREDITS.md`), `services/exampleSongs.ts` (`openExampleSong`: fetch, then the normal MIDI import with the catalog's tracks/transposition, credits written into the song info before loading finishes so the song is clean), `components/ExampleSongsModal.vue` (Play/Open, sections by `kind`). Songs written in code ("Open Road" `demoArrangement.ts`, "Back Porch Shuffle" `exampleShuffle.ts`) share `data/songBuilder.ts`; MIDI examples can give non-guitar tracks their own strings (`buildSongFromMidi` option `tunings`) and a clef. Opened from the File group (`exampleSongs` action), the phone ⋯ menu and the first-run card. "Open Road" is the built demo.
  - Lyrics: GP4/GP5 store one lyric track with five lines (start bar + text), GPIF stores the same lines on the track (GP7 also a copy per beat, which wins); both are put on the beats with `applyLyricLines`. GP text is decoded as UTF-8, else Windows-1252.
- **Export** is the lazy `songExport` chunk: `.gt` (`utils/gtSerialization.ts`, LZ-compressed text), GP5 (`gp5Export.ts`), GPX (`gpifExport.ts` + `gpxWriter.ts`), MusicXML 4.0 (`musicXmlExport.ts`; drums as one instrument per drum note with `<midi-unpitched>`, chords as `<harmony>`), Standard MIDI File type 1 (`midiExport.ts`: conductor track plus one track per song track, in played order from `buildPlayOrder` or bars as written; velocities from `utils/noteVelocity.ts`, the table the SoundFont player uses), GP7/8 `.gp` (the GPIF in a stored ZIP with `VERSION`, `buildGpFile` in `gpxWriter.ts`; stored: fflate's compressor wasn't worth the bytes; fflate itself is the lazy `zip` chunk since Big win 30), PDF and SVG of the rendered sheet (`pdfExport.ts`, `tabExportSvg.ts`).
- **Printing** (`services/printView.ts`, lazy chunk `print` with `utils/printPagination.ts`): File → Print composes the whole tab (tab + classical, `composeFullTabExportSvg`), splits it into A4 pages of whole rows (`paginateRows`, row bands from the render layout), adds a running title from page 2 and "Page n of N", appends `#printView` and calls `window.print()`; the print style sheet (`guitarTab.scss`) shows only `#printView`, the light theme is forced while printing. The PDF export uses the same pages.
- **Persistence:** `songAutosave.ts` keeps up to 10 snapshots in IndexedDB while there are unsaved changes ("dirty" compares song content with the last clean point), offers recovery on startup and guards against closing with unsaved changes. Cloud songs (`cloudSongApi.ts`, `cloudSongLoader.ts`, `CloudSongsModal.vue`) are optional and need a server that is not in this repository.

## Events and settings

- `utils/typedEventBus.ts` is the only event bus, typed by the `AppEvents` map: `song-data-changed`, `song-loaded`, `selection.*`, `playback.*`, `classical-notation-changed`, `modal.*` and a few `navigation.*`/`ui.*` events. New state that components only display should be a store plus a `computed`, not an event.
- Settings are `stores/settingsState.ts` (imported as `Settings`): reactive, each key persisted to `localStorage`. `EPSILON` and `OVERBAR_ROW_HEIGHT` are constants exported there.
- Banners: `showNotification(text, kind, action?)` in `stores/notificationState.ts`, shown by `App.vue`; `showUserError` (`services/userNotifications.ts`) wraps it.

## Bundle

Chunks are assigned by `manualChunks` in `vite.config.ts`, and `scripts/check-bundle-budget.mjs` (`npm run build:check`) enforces a size budget per chunk, fails if two chunks import each other, and checks the startup set: the entry plus every chunk it imports statically must stay under 500 KB (471 KB after Big win 30, 550 before), and a list of chunks (dialogs and their handlers, the Guitar Pro readers, fflate, colour picker, editing tools, VexFlow, exports, note menu, phone UI) must not be in it. `playwright.startup.config.ts` runs `e2e/*.prod.spec.ts` against `vite preview` (time to editor ready, first paint, JS before ready, longest task, dialogs not yet mounted) with generous limits; CI runs it after the build.

- At startup: the entry (`App.vue` and the shell, 16 KB budget), `framework` (Vue, plus the Vite/Vue helper modules), `vendor`, `serialization` (lz-string), `shortcuts`, `toolbar` (`Menu.vue` and `components/toolbar/`, 32 KB), `icons` (AppIcon and the icon map, 40 KB), `studio-ui`, `tab-renderer`, and `editor-core` (228 KiB of 240 since Big win 30; 306 before): stores, utils, the editor, playback and audio, the dialog ids and open/close, the .gt reader, fastdom and the riff. The `shortcuts` table is 8 KB.
- On demand: `editing-tools` (8 KB: rhythm keys, keyboard selection, transpose; loaded with `import()` on first use, and keys pressed while it loads wait for it in `keyboardDispatch`), `dialog-handlers` (21 KB), `dialog-shell` (`BaseModal`, focus handling, form controls) and one chunk per dialog component, `ModalsContainer` and `studio-panels` (with the first dialog), `gp-import` (GP3–8 readers, 31 KB) and `zip` (fflate) when a Guitar Pro file is opened, `cursorAnnouncer`, `color-picker` (vanilla-picker: track settings and marker dialogs), the note menu (`NoteMenu`), the phone UI, `classicalNotation` + `notation` (VexFlow, 1 MB), `songExport`, `pdfExport`, `musicXmlImport`, `demoArrangement`, `cloudSongLoader`, `compactLayout`.

`editor-core` is one chunk because its modules import each other. When two chunks import each other, the browser runs one before the other has initialized, and the production build fails at startup with "Cannot access 'x' before initialization" while the dev server works (HANDOVER 3.34). To make part of it lazy, remove the static imports back into it first, as Big win 30 did for the dialog handlers (`dialogs.ts` imports the registry with `import()`) and the Guitar Pro readers (`importSongFile` loads `import/guitarProReaders.ts` and passes it in; `importSongBytes` stays synchronous for `.gt` and refuses a GP file whose reader wasn't passed).

## Tests

- **Unit** (Vitest, `tests/`, runs in node): pure modules directly; DOM tests opt in per file (`happy-dom`, or `jsdom` for XML). Characterization snapshots pin behaviour that was ported: playback (`playbackCharacterization.test.ts`), the audio graph on a fake AudioContext (`audioEngine.test.ts`), GP3/4/5 import from byte-built files (`guitarProImport.test.ts`), the `Song` facade, note entry and classical conversion. Coverage floors per folder are in `vite.config.ts`.
- **E2E** (Playwright, `e2e/`, desktop Chromium and a Pixel 7 profile) runs against the Vite dev server and drives the app through its own modules (`await import('/src/stores/song.ts')` inside `page.evaluate`). It covers editing, undo, shortcuts, playback and navigation, practice, import fixtures and fuzzing, GP5/GT/MusicXML roundtrips, the phone layout, and screenshot baselines for classical notation and the sheet (per OS: `win32` locally, `linux` from CI).
- **CI** (`.github/workflows/ci.yml`): unit tests with coverage, typecheck, lint, `build:check`, the startup budget on the built app, Playwright on Linux with a generated stand-in SoundFont.

## Known weak spots

- `Song` is still a global mutable object that any service can write, and `audioGraph` and `playback` are singletons created on import. `AudioGraph` takes its `AudioContext` (so an `OfflineAudioContext` could render), but `playback` and the sample player still use the one `audioGraph`; unit tests stub that module.
- The desktop toolbar is no longer mounted on phones, but the sequencer, effects bar and footer still are (hidden).
- The first layout at startup costs ~120 ms on desktop Chromium (a second one ~90 ms) while a full re-layout of the same page takes ~7 ms; not caused by the web fonts, images, form controls or one part of the DOM (HANDOVER 3.42). Not understood yet.
- The rest of `editor-core` is still one cyclic cluster (editor, playback, audio, stores).
- The tab layout re-runs as a whole on any `renderVersionState.song` bump; rows don't yet depend on their own bars' versions.
- `renderBridge.ts` (layout lookups for playback and navigation) and `renderEventBridge.ts` (navigation events) keep their old names; `durationReplacerAdapter.ts` is a real conversion layer (Beat ↔ the replacer's beats).
- 26 lint warnings (complexity, function length, `any`), mostly in ported code: the GP5 writer, `durationEditing`, `barFilling`, `computeBarWidth`, `manualChunks`.
